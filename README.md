# jinsei-inc

人生Inc.——人生を、会社として運営します。自分の外側に、**もう一つの脳と、動く腕**を置く仕組みです。

---

## これは何か

**外部脳です。** 判断軸・思想・決めた経緯・好き嫌いが、自分の頭の外に溜まっていきます。「なぜそう決めたのか」が、決めた本人より正確に残ります。

**腕でもあります。** 溜まった記録は、置いてあるだけではありません。部署があって、それぞれに担当のAIエージェントがいて、時間が来たら勝手に動きます。調べる、まとめる、思い出させる、反論する——**自分が「やったほうがいいと分かっているのに、やらない」作業のほうを、代わりに手が動きます。**

**結果として、自分の拡張になります。** 記録が増えるほど、エージェントは自分をよく知っている相手になります。毎回ゼロから事情を説明する必要がなくなり、「それは3ヶ月前にこう判断している」と返してくるようになる。

いわゆる「第二の脳」と呼ばれるものに近い場所から始まりますが、**脳だけでは止まりません。** 記録する装置ではなく、**記録に対して定期的に何かが起きる装置**です。そこが要点です。

## 実際に何が起きるか

**起動したとき。** その日のダッシュボードが出ます——今月立てた問い、期限が近いプロジェクト、溜まっていて処理されていないもの、放置日数が閾値を超えた儀式。自分で思い出す必要はありません。閾値の判定はスクリプトが持っていて、人間の記憶に依存させていません。

**話している途中。** 「やっぱりこっちのほうがいい」「それは違う」——判断軸がにじんだ瞬間に、秘書役がその場で記録します。**「メモして」と言う必要がありません。** 会話が長くなると気づきは消えるので、言われてから書く設計にしていません。

**週末。** その週の日次ログが週次のまとめに圧縮されて、元は消えます。溜めっぱなしにしません。消す前に「判断軸が拾い漏れていないか」を確認する手順が入っています。

**月末。** 溜まった判断軸の原文から、繰り返し出てくるものだけを抽出して精錬します。同時に、古くなった決定の棚卸しと、蓄積された人物理解の本人突き合わせをやります。**合わなくなった判断軸は消さずに「卒業」と印を付けて残します。**

**過去の判断を引くとき。** ここだけ作法が決まっています。「2月の判断・5ヶ月前」と初出日と経過期間を添え、三人称で引用し（「当時のあなたはこう判断している」）、**必ず反証の問いを1つ返します**——「当時の前提のうち、今変わっているものはあるか」。

理由は、過去の自分に頼れることと縛られることが同じ仕組みの表と裏だからです。材料として出したつもりでも、提示した時点で判断は引っ張られる。だから引用には毎回ブレーキを付けてあります。

**重い調べもの・考えものが出たとき。** 担当の部署に投げます。別の文脈で動くので、こちらの会話の流れに引きずられません。**反対役を立てることもできます**——ただしそれには限界があって、その限界は [docs/limits.md](docs/limits.md) に書きました。装置の中の反対役は却下が無料なので、本物の他人の代わりにはなりません。

## 何を解こうとしているか

一人で何かを決めていると、**決めた理由が数ヶ月で消えます。** 結論だけが残って、なぜそう決めたのかが思い出せない。だから同じことを何度も考え直すし、前と違う結論を出しても気づきません。

AIに相談する人なら、もう一つ心当たりがあるはずです。**毎回ゼロから自分の事情を説明し直している。** 十分に賢い相手なのに、こちらを何も知らない相手として毎回始まる。

この2つは同じ問題です——**判断の材料が、どこにも溜まっていない。**

だから、やることは3つに絞ってあります。

1. **判断の理由を、決めた瞬間に残す。** 結論ではなく「なぜ」を書きます。後から読む用に整えません（整えようとすると書かなくなります）
2. **溜まったものを読み返す口を作る。** 週次・月次の儀式で強制的に読みます。**出口のない記録は、無いのと同じです**
3. **過去の自分に反論させる。** 上に書いた引用の作法です

そのための入れ物として、人生に「部署」を置きます。AIエージェント（Claude Code）が窓口の秘書役として常駐し、必要に応じて各部署の役を呼び分ける——という運用を、個人用に4ヶ月ほど回してきました。ここにあるのは、そこから型だけを取り出したものです。

動いている実物から、個人情報と個人の記録をすべて抜いてあります。

> 似ているが意識的に採らなかった手法（PARA・Zettelkasten・RAG など）と、まだ埋まっていない弱点は [docs/limits.md](docs/limits.md) にまとめてあります。

## 3つのフォルダ

| | 中身 | どうするか |
|---|---|---|
| `template/` | 構造・ルール・スクリプト・エージェント定義 | **コピーして使う** |
| `examples/` | 記録がどう溜まっていくかの見本 | **読むだけ** |
| `docs/` | なぜこの設計にしたのか | 読むだけ |

`docs/` は**本体1本と補足1本**です。`design-principles.md` が本体（設計判断を他人が適用できる粒度まで抽象化したもの）で、`limits.md`（意識的に採らなかったもの／まだ埋まっていない弱点）が補足です。

> **`examples/` の中身は、すべて架空の人物の創作です。**
> 実際の記録ではありません。実物を見せるための見本ではなく、「4ヶ月運用するとこの粒度のものがこう溜まる」を伝えるために書き下ろしたものです。

## 始める

```bash
git clone https://github.com/eganzin1004/jinsei-inc.git
cp -r jinsei-inc/template ~/my-os
cd ~/my-os
```

このあと何をするかは、コピーした中の **`SETUP.md`** が持っています。段階0から5までのチェックリストで、**秘書役が起動のたびに見て、未完のうち次の1段階だけを出します。** 手順の詳細は [GETTING-STARTED.md](GETTING-STARTED.md) にあります。

読む順番は `SETUP.md` → 必要になった段階だけ `GETTING-STARTED.md` です。逆から読むと、初日に5週間ぶんの手順を読むことになります。

**先に全部埋めようとしないでください。** 8つの部署を一度に立ち上げると、だいたい3日で止まります（`examples/decisions.md` の 2026-02-16 に、架空の人物が同じ失敗をしている記録があります）。秘書役ひとつと決定ログ1本から始めるのを勧めます。

## 動作環境

- **Claude Code** を前提にしています。`.claude/` 配下のエージェント定義・スキルはこの前提です
- **macOS** で書かれています。自動実行に `launchd` を使っているため、Linux / WSL では動きません。cron や systemd timer への置き換えは可能ですが、**こちらでは未検証なので同梱していません**
- 現時点では「読む資料」として出しています。他人の環境でそのまま動かすところまでは面倒を見ていません

## ライセンス

**付けていません。**

つまり、再利用の許諾をしていない状態です。閲覧はできますが、それ以上の権利は明示的に与えていません。

意図的です。あとから緩めることはできますが、一度 MIT などで出すと締めることはできないので、反応を見てから決めます。使いたい場合は、構造と考え方を読んで自分の手で書き直してください——**そのほうが結局うまくいきます。** 他人の判断軸をコピーしても、自分の判断には使えないからです。

収録しているファイルはすべて自作です（第三者由来のものは含みません）。

## 続けるつもりの範囲

- 更新は月1回程度です。運用している実物から生成し直して同期します
- Issue・PR への応答は保証しません。読まないかもしれません
- この形式そのものを製品にする予定は今のところありません

放置されていても、置いてあるものは読めます。それで足りる想定で出しています。
