# 人生OS

## 設計思想

このフォルダは3つの機能で構成されています。

- **外部脳** — 思想・判断軸・経緯・嗜好を記録する
- **自分を理解する存在** — 記録から人物理解を蓄積する（`strategy/mindset.md` → `strategy/persona.md`）
- **運営組織** — 部署と儀式で、人生のあらゆる取り組みを回す

3つ目が要点です。記録だけなら他のツールでもできますが、**記録に対して定期的に何かが起きる仕組み**がないと、書いたものは読まれません。

## なぜ作るのか

```
（ここに自分の動機を1〜2段落で書く。記入例: 課題解決のために作ったのではなく、
作ること自体が楽しくて続けている。同時に、作って育てることが結果として生活を
良くしている。この二つに順序はない）
```

**この節を空にしないでください。** 動機が書いていないと、3週間後に「これは何のためにやっているのか」が分からなくなり、そこで止まります。

## オーナー

要るのは、AIが判断の前提に使える最小限の事実だけです。**ここに書いた属性は全部署の判断の前提として毎回効くので、書きすぎないほうがいいです。**

```
- 名前 / 呼ばれ方:
- 仕事: （職種・雇用形態・働く場所）
- 開発環境: （どのエディタ・どのフォルダ配下で作業するか）
- 嗜好・人物理解: life/profile/ ／ strategy/persona.md を参照
```

## 直下の構成

直下は**部署（フォルダ）とルートファイル**で構成します。

- **部署** = 永続的な機能（プロジェクトが終わっても残る）
- **プロジェクト** = 部署をまたぐ一時的な取り組み（`projects/` で管理）
- 各部署に **subagent** = 並列で、独立した文脈で動かせる

### 部署一覧

| 部署 | フォルダ | subagent | 役割 |
|---|---|---|---|
| 秘書室 | secretary | company-secretary | 窓口・調整・タスク・日次ログ。常設 |
| 戦略室 | strategy | company-strategy | 方向性・長期ビジョン・判断軸の蓄積 |
| 開発部 | engineering | company-engineering | 技術設計・実装・デバッグ |
| リサーチ部 | research | company-research | 市場調査・競合分析・技術調査 |
| 事業開発部 | ventures | company-ventures | マネタイズ・ビジネスモデル |
| クリエイティブ部 | creative | company-creative | デザイン・ビジュアル・ブランド |
| ライフ部 | life | company-life | 健康・習慣・家族・日常の質 |
| 経理部 | finance | company-finance | 資産管理・支出分析・月次レポート |

**8つ全部を一度に立ち上げないでください。** 秘書室ひとつと `notes/decisions.md` 1本から始めて、同じ領域の作業が2回繰り返されたら足すのが順番です。

### ルートのファイル

| ファイル | 役割 |
|---|---|
| `CLAUDE.md` | 全部署共通の行動原則・ドキュメント規約（このファイル） |
| `MANUAL.md` | 仕組みの説明書。**ルールの正はCLAUDE.md群、判定ロジックの正は `scripts/`** ——MANUAL.mdは説明であって規範ではない |
| `SKILLS.md` | 自作スキルの台帳 |
| `ARSENAL.md` | 外部から取り込んだスキルの台帳 |
| `_department-template.md` | 新部署のテンプレート |

### 実行系

`scripts/` と `.claude/` が第3の構成要素です。**チェックの判定ロジック（対象・閾値・条件）の正は `scripts/` にあり、CLAUDE.md群には条件を書きません。**

| 場所 | 中身 |
|---|---|
| `scripts/` | 起動時チェック・自動メンテ・整合性監査・月次レビュー準備 |
| `.claude/agents/` | 部署subagentの定義 |
| `.claude/skills/` | スキルの実体（台帳は `SKILLS.md` / `ARSENAL.md`） |

> 🔒 の印が付いたファイルは、`.gitignore` で追跡から外す機微ファイルです。**何を機微にするかは自分で決めます。** `template/.gitignore.sample` に雛形があります。リポジトリに入れないぶんのバックアップは別に用意してください（クラウドストレージへのミラー等）。

## 全部署共通の行動原則

秘書室に限らず、すべての部署がこれに従います。

- **窓口は秘書室ひとつ。** 部署の作業が必要なときは秘書室がsubagentを呼びます
- **プロジェクトと部署を混ぜない。** 背景・目的・意思決定は `projects/`、技術ナレッジ・調査結果は部署フォルダへ
- **外部サービスへの書き込みは非対称に扱う。** 追加（タスク・予定の作成）は許可なしでよく、都度報告。**完了化・削除は毎回、対象一覧を見せて明示の許可を取ってから**。読み取りは自由。追加は消えるものがないが、消す操作は取り返しの感覚が違うため
- **環境を変える前に案を見せる。** 設定・スクリプト・agent定義・ルールファイルの変更は、適用前に案を出して許可を取ります。日々のログ・タスク・アイデアは即時でよい
- **モデル名を焼き込まない。** 特定のモデル名を設定やスクリプトに固定せず、エイリアスか「未指定＝継承」を使います。モデル変更が1箇所で済むように
- **外部脳を読んでから答える。** 方向性の相談に答える前に `strategy/mindset.md` と `secretary/notes/decisions.md` の関連項目を確認します。過去の判断軸と矛盾しそうなら明示的に引用します
- **引用には作法がある。** 過去の判断を引用するときは4つ守ります。①**初出日と経過期間を添える**（「11月の判断・8ヶ月前」）②**三人称で引用する**（「当時のあなたは〜と判断している」）③**反証の問いを1つ返す**（「当時の前提のうち、今変わっているものはあるか」）④**見積もりを聞かれたら過去の数字を先に出さない**。理由: 材料として出したつもりでも、提示した時点で判断は引っ張られます。**過去の自分に頼れることと、縛られることは同じ仕組みの表と裏です**
- **本番に上げる前に、実際のstaging環境で確認する。** ローカル確認と混同しません
- 公式・信頼できるツールだけ使います

## ドキュメント規約

CLAUDE.md群は更新され続ける前提です。**「今のルール」だけを現在形で書きます。**

- 日付・経緯・反省エピソードをルール本文に書かない。行動を縛るのに必要な「なぜ」は1行の原則として残してよい（物語になったら履歴側へ移す）
- 3レイヤーの分担: **状態**＝CLAUDE.md群（現在形・日付なし）／**履歴**＝`secretary/notes/decisions.md`（日付つき）／**価値観**＝`strategy/mindset.md`（普遍化した判断軸）
- ルールを変えたら、旧文は残さず書き換える。決定と経緯は履歴側に追記し、矛盾する古い決定に廃止マークを付ける。ルールファイルの過去はgitと履歴が持つ
- 末尾に `最終更新: YYYY-MM-DD` を1行置く（鮮度の目印。本文中の日付とは別物）
- 時系列で増えるファイル（履歴・ログ系）は**古い順・末尾追記**で統一する。並べ替えない——最新は常に末尾にある
- **台帳やログを新設するときは、入口（誰が・何をきっかけに書くか）と出口（誰が・何をきっかけに読むか）をセットで設計する。** 出口を設計できないなら作らない、または既存の儀式に統合する。**出口のない台帳は、書かれても使われず死にます**

## アカウント構造

外部サービスのアカウントを3層に分けて把握します。**この設計自体が型として効く部分**で、どこに何を書くと誰に見えるかが事前に決まります。

| 層 | 用途 | 備考 |
|---|---|---|
| 個人 | 自分のメイン | |
| 共有 | 家族・パートナーとの共有 | 共有カレンダー・共有ワークスペース等 |
| アクセス不可 | 相手個人のもの | **読めないが、存在することは記録しておく。** 書けないものを把握していないと、AIが読める前提で提案してきます |

この表の右端に自分のアカウントを書き入れてください。
