# 説明書

> **これは何か**: この仕組みの全体像を一望するための文書です。「これは何で、どう動いていて、なぜこの形なのか」を1本にまとめてあります。
>
> **なぜ別枠なのか**: ドキュメント規約が「今のルールだけを現在形で書く／経緯を本文に書かない」と定めているので、**設計の全体像と理由を語る散文の居場所がどこにもなくなりました。** この文書はその空白を埋めるためにあります。
>
> **入口**: 大きな構造変更のとき、または整合性監査で追随漏れを指摘されたときに更新します。日々のルール変更では触りません。
> **出口**: 全体を把握したいとき／新しいセッションがこの仕組みを理解する入口／外部発信の材料。
>
> **ルールの正はここではありません。** 行動を縛るルールの正は `CLAUDE.md` 群、判定ロジックの正は `scripts/`。この文書は説明であって規範ではないので、食い違ったらルール側が正しいです。
>
> 設計原則・選ばなかった選択肢・既知の弱点は `docs/` にあります（この文書には書きません。同じことを2箇所に書くと片方が古くなります）。

# 第1部 これは何か

## 1-1. 一段落での説明

> **自分の判断軸と経緯をAIが読める形で残し続け、AIがそれを読んで日々の運営を回す仕組みです。対象は知識ではなく自分自身で、記録はいつでも人間が読めるプレーンテキスト、置き場所はローカルのgitリポジトリです。**

実体は Markdown ファイル群と、それを走らせる数本のbashスクリプトだけ。データベースもアプリもありません。「会社」というメタファーを採り、秘書室・戦略室・開発部といった8部署にエージェントを置いて、人生のあらゆる取り組みを部署とプロジェクトとして運営します。

## 1-2. PKM・セカンドブレインとの距離

**PKMではありません。** PKMの対象は「知識」——外から得た情報を後で取り出せる形に整理する装置です。ここでの対象は「自分」です。何を大事にしているか、過去にどう判断したか、どういう癖を持った人間か。記録されるのは読んだ本の要約ではなく、迷いながら決めたことと、その理由です。

PKMが賢くなるための装置だとすれば、こちらは**自分を理解して人生を回すための装置**です。この違いは運用のあらゆる場所に効きます。たとえばPKMではノートを消すことに強い抵抗がありますが、この仕組みは日次ログを週次で圧縮して消します。知識は取っておく価値がありますが、日々の作業ログは判断軸を抽出したあとは重みが下がるからです。

呼び名としては **Life OS** が最も近く、GitHubの `life-os` トピックには数十のリポジトリが並んでいます。この潮流はまだ勝者が決まっていません。

## 1-3. 何のために作られたか

### 課題解決のために作ったのではない

出発点は「困っていることを解決するため」ではありません。**作ること自体が楽しくて続いていて**、同時に**作って育てることが結果として生活を良くしている**。この二つに順序はなく、両方本当です。

### 「楽しいから作っている」は設計上の前提である

弁明として書くと説明書としての価値が半分死ぬので、設計前提として書きます。

**この領域で放棄されたシステムの証言には、共通して苦痛の言語があります。** 「システムを使うより保守している時間の方が長かった」「ノートを書く時間よりフォーマットする時間の方が長い」。7年・1万ノートを全消去した書き手は、自分の第二の脳を「霊廟」と呼びました。過去の自分と過去の興味の、埃をかぶったコレクションだと。

対して、続いているものの作り手は例外なく楽しんでいます。

**個人システムの生存を決めているのは、機能でも構造でもなく、作り手がそれを楽しんでいるかどうかです。** 楽しんでいる限り触られ続け、触られている限り腐りません。義務になった瞬間に死にます。

だから「楽しい」を副産物ではなく**燃料**として扱います。帰結は2つ。

1. **効率だけで機能の可否を決めない。** 「使わないかもしれないが作ってみたい」を全否定しません。ただし出口設計の規約は通します（作ってよいが、読まれる経路は考える）
2. **儀式を義務にしない。** 意志力に依存する仕組みは作らず、発火は自動化して、人間には判断だけを残します

### 「維持コストが低い＝正義」ではない

いちばん誤解されやすい前提です。「保守コストがほぼゼロになるから保守され続ける」は正しいのですが、これを最後まで押すと危険な地点に着きます。

エージェントに毎朝デイリーノートを自動生成させている実践者が書いていました——「人間が見ない場合、手段の目的化は原理的に起きない」。効率としては完璧です。しかし同じ書き手が続けてこう書いています。「**真っさらなデイリーノートを開いて考える自由がない。**」AIが立てた計画とチェックボックスが既にそこにあり、人間は確認・修正・実行の立場に転じる。

**効率化を進めすぎて「自分で考える余地」が消えることのほうが、維持コストが高いことより危険です。** 外注される事務作業——ファイリング、相互参照、要約——こそが理解の生まれる場所なので、全部渡すと**自分が内面化していない立派な記録**が手に入ります。

# 第2部 どう動いているか

## 2-1. 全体アーキテクチャ

3層に分かれています。

| 層 | ファイル | 書き方 |
|---|---|---|
| **状態** | CLAUDE.md群 | 現在形・日付なし・旧文を残さない |
| **履歴** | `secretary/notes/decisions.md` | 決定・経緯・日付つき・追記のみ |
| **価値観** | `strategy/mindset.md` | 普遍化した判断軸 |

これを全体に広げると次のようになります。

```
┌─ Schema（人が書き、機械とLLMが読む）─────────────────────────────┐
│  [LLMが読む宣言的スキーマ]        [bashが実行する判定スキーマ]    │
│   CLAUDE.md（組織ルール）          scripts/startup-check.sh       │
│   {部署}/CLAUDE.md × 8             scripts/auto-maintain.sh       │
│   .claude/agents/*.md × 8          scripts/consistency-check.sh   │
│   .claude/skills/*/SKILL.md        scripts/monthly-review-prep.sh │
│   SKILLS.md / ARSENAL.md           .gitignore（機微の線引き）     │
└──────────────────────────────────────────────────────────────────┘
      │ 読む・従う                    │ 判定する・書き換える
      ▼                               ▼
┌─ Wiki（AIが書き、人間が読む）────────────────────────────────────┐
│  strategy/mindset.md      月次精錬の出力（普遍化した判断軸）      │
│  strategy/persona.md 🔒   観察された人物像（✓/未確認ステータス）  │
│  secretary/notes/current-setup.md    環境の現在地                 │
│  secretary/notes/weekly/*.md         日次ログの圧縮結果           │
│  projects/*.md                       プロジェクト台帳             │
│  strategy/reviews/*.md               月次レビュー（日付つき凍結） │
└──────────────────────────────────────────────────────────────────┘
      ▲ 精錬・圧縮・生成              ▲ 参照
┌─ Raw（不変の原本）───────────────────────────────────────────────┐
│  git履歴                                                          │
│  secretary/notes/decisions.md  追記のみ（ステータス行だけ可変）    │
│  strategy/mindset-log.md 🔒    完全追記・削除禁止（真のRaw）       │
│  secretary/ideas/*.md          会話中のアイデア原文               │
│  secretary/notes/YYYY-MM-DD.md 日次ログ（週次圧縮で消える一時Raw）│
└──────────────────────────────────────────────────────────────────┘

┌─ 外部の正（この3層の外・こちらは台帳を持たない）──────────────────┐
│  タスク管理サービス      TODOの正                                 │
│  カレンダー              予定の正（こちらは当日キャッシュのみ）    │
│  家計簿サービス／証券会社  資産の一次データ（手動でCSVを取り込む） │
└──────────────────────────────────────────────────────────────────┘
```

### この図で押さえるべき4点

**(a) Schema層は2種類に割れています。** ルールファイルは繰り返し「判定ロジックの正はスクリプト」「ここに条件を書き足さない」と明記しており、**LLMが読む宣言的スキーマ**と**bashが決定論的に実行する判定スキーマ**を意図的に分離しています。「LLMに判定させない」という設計判断の表れです。

**(b) `weekly/` は Wiki ですが Raw を兼ねています。** 週次圧縮は日次ログ（Raw）を要約して `weekly/` を作り、元を削除します。圧縮後に残る一次記録はgit履歴だけになります。

**(c) `decisions.md` は純粋なRawではありません。** 追記のみですが、ステータス行だけは後から「廃止」に書き換わります。本文は消しません。

**(d) 機微ファイルにはRaw層がありません。** `.gitignore` で除外されているのでgit履歴に入らず、バックアップは外部ストレージへのミラーだけです。世代を持たない上書きミラーなので、「追記のみで削除しない」というルールで守られているだけで、**機械的な履歴保証はありません。** 3層モデルの穴です。

## 2-3. 情報のライフサイクル

```
                   ┌──────────────┐
    自分の発言 ────┤ 秘書役       ├── 判断軸/価値観 ─▶ strategy/mindset-log.md（原文・追記のみ）
                   │ （メイン     ├── アイデア ──────▶ secretary/ideas/YYYY-MM-DD.md
                   │   セッション）├── 作業の結論 ────▶ secretary/notes/YYYY-MM-DD.md
                   │              ├── 決定 ──────────▶ secretary/notes/decisions.md
                   │              ├── タスク ────────▶ 外部サービス（正）
                   │              └── 部署委託 ──────▶ subagent → 部署フォルダ
                   └──────────────┘
                             │
       ┌─────────────────────┼─────────────────────┐
       ▼ 週次（自動）         ▼ 月次（人が発動）      ▼ クローズ時（人が発動）
  weekly/ 生成＋日次削除   mindset.md 精錬        persona.md / growth-log.md 追記
  current-setup.md 更新    decisions.md 棚卸し    整合性監査の提案
  git 自動コミット         ideas/ 棚卸し
                           生存確認棚卸し
```

### 発言 → 原文ログ → 月次精錬 → 判断軸

二段構えにする理由は**コンテキストが長くなると会話は圧縮され、会話中だけにある気づきが失われる**ことです。ファイルに書いたものだけが残ります。

| 段階 | 誰が | きっかけ |
|---|---|---|
| ① 原文追記 | 秘書役（依頼を待たない） | 「やっぱり〜」「〜は違う」など判断軸が滲む発言をその場で検知。重複可・漏らさない優先 |
| ② クローズ時スキャン | 秘書役 | セッションを閉じるとき。「もう書いた」で飛ばさない |
| ③ 圧縮時の漏れ拾い | 週次圧縮の自動処理 | 週次 |
| ④ 月次精錬 | 戦略室 ＋ 自分 | 人生軸→`mindset.md`／技術知見→`engineering/docs/`／人物像→`persona.md` |
| ⑤ 鮮度監視 | 起動時チェック | 最終精錬から一定日数を超えたら警告 |

原文ログは削除しません（追記のみ・永続）。精錬版への直接追記はしません。

### 日次ログ → 週次圧縮 → 削除

```
secretary/notes/YYYY-MM-DD.md（日次・Raw）
      │ トリガー: 今週と異なるISO週の日次ログを検出
      ▼
  LLMに要約させる
      │  ① 対象ログを読む
      │  ② weekly/YYYY-WNN.md を作成/追記（冒頭に元ファイル名を必ず含める）
      │  ③ 判断軸が原文ログにあるか確認し、漏れを追記
      │  ④ current-setup.md を更新
      │  【重要】日次削除と git commit はLLMにやらせない
      ▼
  呼び出し元のスクリプトが検証（weeklyが新しい && 日次ログ名が本文にある）
      ├─ OK → 日次ログを削除
      └─ NG → 日次ログを温存
```

**判断軸の移送は削除より先。** 検証をLLMではなくbashにやらせているのが要点で、「LLMが仕事をしたと言っているか」ではなく**成果物が実在するか**で判定しています。

### 意思決定 → 累積ログ

追記の前に必ず検索して、矛盾する既存決定がないか確認します。あれば旧決定の**本文はそのまま、ステータス行だけ**書き換えます。削除しません——廃止になった経緯も思考の履歴です。

出口は3つ。①月次レビューの棚卸し（古くて有効なままの決定を列挙して廃止漏れを拾う）②行動原則「外部脳を読んでから答える」③起動時チェックの通知。

### 人物観察 → `persona.md`

リアルタイム追記は**しません**（入口は原文ログ一本）。クローズ時の振り返りスキャンで【未確認】として追記し、月次レビューで本人に突き合わせて✓に昇格します。**✓にできるのは本人突き合わせのみ**で、AIの判断では昇格させません。

秘書役は**起動時にはこれを読みません**（呼ばれる前に人物像を持ち出さない）。壁打ち・人生の相談・文章の依頼のときだけ読みます。

併走する `growth-log.md` は同じスキャンで「できた」「乗り越えた」を拾います。**自己申告を待ちません**——成功を割り引く癖がある場合、気づく役目はAI側が持ちます。

### タスク → 外部サービス

**TODOファイルは存在しません。** 正は外部のタスク管理サービス側です。理由は、外にいるとき手元で足せることだけです。

マーク体系と表示ルールは `secretary/CLAUDE.md`。**完了化・削除は毎回明示の許可が必要**です（非対称ルール）。

### アイデア → 二入口

セッション中の入口が `secretary/ideas/`、外からの入口が外部のメモサービス。**合流点は月次レビューの棚卸し**で、両方を見返して「動かす／寝かす／閉じる」に仕分けます。

### 当日限りキャッシュ

カレンダーなどのキャッシュは自動メンテが当日分以外を削除します。正確には「当日限り」ではなく**「自動メンテが次に走るまで」**で、マシンがスリープしていれば翌日以降も残ります。

## 2-4. 儀式一覧

### 自動発火（人の操作なし）

登録は**1本だけ**（ログイン時＋数時間おき）。ロック付き・冪等で、溜まっていなければ数秒で終わります。

| # | やること | 条件 |
|---|---|---|
| ① | カレンダーキャッシュ取得 | 当日分が無いとき |
| ② | 週次圧縮（生成 → **スクリプト側で検証してから**日次削除） | 今週以外のISO週の日次ログがあるとき |
| ③ | 使い捨てファイルの掃除 | 毎回 |
| ④ | git自動コミット（**pushはしない**） | 差分あり かつ 直近30分にファイル変更なし（＝セッション中でない） |
| ⑤ | 外部ストレージへのバックアップ | 前回から7日以上 |

**自動メンテがやらないこと**: 月次レビュー・判断軸の精錬・アイデア棚卸し（＝判断が要る作業）、リモートへのpush、機微ファイルのミラー。

### 起動で発火（コマンド1つがトリガー・以降は自動連鎖）

`/company` → ①`startup-check.sh` 実行 ②ルールを読む ③タスク取得 ④必要ならカレンダー取得 ⑤ダッシュボード表示。

起動時チェックは十数項目を機械判定します。**閾値の正はすべてこのスクリプトにあり、ルールファイル側には条件を書きません。**

### 会話中に発火（明示依頼なし）

判断軸のリアルタイム保存／アイデアのリアルタイム保存／タスクの即時登録／部署委託。

### セッションクローズで発火

**5点セット**——①作業ログ ②判断軸の追記漏れスキャン ③決定ログの同期＋廃止マークチェック ④振り返りスキャン ⑤台帳の更新。**5項目を毎回名指しで並べ、該当なしは「該当なし」と書きます**（「n点セット済み」で済ませない）。

ルールを変えたセッションでは整合性監査を提案します。

### 週次・月次・年次

| 儀式 | トリガー | 実行主体 |
|---|---|---|
| 週次圧縮（手動版） | 起動時チェックが警告を出したときだけ | 秘書役。自動版にない**機微ミラー**を含む |
| 月次レビュー | 毎月末。未実施なら**実施されるまで毎回**警告 | 戦略室 ＋ 自分。**反対役**の手順を含む |
| 判断軸の精錬＋卒業判定 | 月次レビュー内（＋鮮度切れで警告） | 戦略室 |
| 家計月次 | 先月分が未作成で警告 | 経理部 |
| 第三者診断 | **年1**（年次レビューの前段） | 内部の文脈を持たない相手。結果は内部レビューを通してから落とし込む |
| 年次レビュー | 年末 | 戦略室。`vision.md` の年1の出口を兼ねる |

### 自動／手動の4段構造

```
  完全自動（人が何もしなくても走る）
    └─ 自動メンテのみ（登録1本）

  半自動（人はコマンドを1つ打つだけ。以降は連鎖）
    └─ 起動時チェック十数項目 → 各スキルの自動実行

  督促つき手動（走らないと起動時チェックが警告を出し続ける）
    └─ 週次圧縮（例外時）/ 機微ミラー / 月次レビュー / 判断軸の精錬 / 家計月次

  完全手動（誰も催促しない）
    └─ 年次レビュー / 整合性監査 / リモートへのpush
```

**「督促つき手動」という中間層があるのが構造上の特徴です。** 人間の記憶ではなく、スクリプトの閾値判定が督促の主体になっています。

## 2-5. 依存関係とロックインの境界

**データ層はロックインゼロ。** 中身はすべてプレーンな Markdown ＋ CSV ＋ bash で、バイナリ形式・独自DB・ベンダー固有フォーマットは一切ありません。`scripts/` のうち3本はLLMを呼びません。**例外は `auto-maintain.sh`** で、カレンダー取得と週次圧縮でLLMを2箇所呼びます。

**AIエージェントがなくなったら:**

```
【残るもの】
  ● 全Markdown・CSV／git履歴／リモートのリポジトリ／外部ストレージのバックアップ
  ● scripts/ のうち startup-check・consistency-check・monthly-review-prep
  ● 外部サービス側のデータ（タスク・カレンダー・メモ・家計）
  ● ルールの「内容」——読めば人間でも他のAIでも同じ運用を再現できる

【動かなくなるもの】
  ✕ ルールの自動読み込み（誰も読まないルールになる）
  ✕ 起動シーケンス・ダッシュボード
  ✕ 部署subagentの並列起動・振り分け／スキルすべて
  ✕ 週次圧縮の要約生成／判断軸の精錬／人物観察の生成
  ✕ 自動メンテのうち①カレンダー取得・②週次圧縮（③〜⑤は残る）
```

移植コストは「①LLMランナーを差し替える ②呼び出し2箇所を書き換える ③skill/subagent起動の同等物を用意する」の3点に集約されます。逆に言えば、**判断を伴う儀式はLLMなしでは成立しません**——これはロックインというより、そもそもLLMを前提に設計された機能です。

## 2-6. 変更が伝播する経路

```
ルールを変える（例: 保存先の変更）
  1. 該当 CLAUDE.md を書き換える（旧文は残さない）
  2. 末尾の「最終更新」を書き換える
  3. decisions.md に決定と経緯を追記
  4. 矛盾する旧決定に廃止マークを付ける（その場で。検索して探す）
  5. クローズ時、秘書役が整合性監査を提案する
       └─ 機械層: consistency-check.sh（パス実在・台帳突合）
       └─ 意味層: subagent が波及先の矛盾・古い前提を洗う
       └─ この文書の追随確認（説明であって規範ではないが、
          ルールが変われば必ずずれる。監査対象から外さない）
  6. 指摘はチャットのみ。修正は承認後（環境変更ルール）
  7. 月次レビューの生存確認棚卸しで、出口を失ったファイルを畳む
```

## 2-7. 記録の粒度について

明示しておくべき事実が3つあります。

- **git履歴の粒度は「1日1コミット」。** 自動コミットは1日分に集約されるので、Raw層としてのgitは日単位のスナップショットであって、発言単位の履歴ではありません
- **機微ファイルには履歴層がありません**（→ 2-1(d)）。誤削除・誤上書きは、ミラーが次に走った時点で失われます
- **`scripts/` は組織ルールの構成要素として紹介されていません。** にもかかわらず、閾値・判定ロジックの正はすべてここにあります
