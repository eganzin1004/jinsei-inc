# この仕組みの限界

足りていないものを2種類に分けて書きます。**この2つは似て見えますが、逆を向きます。**

| | 何か | どうするか |
|---|---|---|
| **第1部** | 意識的に**採らなかった**もの | 埋めにいくと悪くなる。埋めない |
| **第2部** | まだ**埋まっていない**もの | 解決していない。埋めていい |

分けてある理由は、**弱点として書かれたものは「埋めるべきもの」に見える**からです。第1部を第2部として読むと、埋めにいって悪くする方向に働きます。

説明書が自己弁護になると価値が消えるので、どちらも率直に書きます。

# 第1部 — 埋めていない（意識的に採らなかったもの）

「まだやっていないこと」ではなく「**やらないと決めたこと**」です。

## 採らなかった手法

| 選択肢 | 判定理由 |
|---|---|
| **PARA / Johnny.Decimal** | **二重分類は害。** 部署メタファーという単一の分類軸で、分類問題は既に解けています。重ねると「これは開発部のResourcesかProjectsか」の判定が毎回発生する。**分類体系は1つなら道具ですが、2つになると仕事になります** |
| **Zettelkasten のアトミックノート** | 目的が違います。あれは**アウトプットを生むために断片を組み替える装置**であり、判断軸の蓄積と人物理解には、アトミック化する動機がそもそも存在しません |
| **Interstitial Journaling** | 出口を設計できません。既存の日次ログと出口が完全に重複します（原則1） |
| **自動減衰（retention decay）** | 週次の能動的削除のほうが優れています。自動減衰は**「なぜ消えたか」が説明できない**（原則4） |
| **RAG / ベクトル検索** | **時期尚早。** grepで足りています。導入の判断基準は「文書数」ではなく「**意味的に似た記述が増えて、エージェント自身が取り違えはじめたとき**」。今やると「作ることの目的化」の典型例になります |
| **Obsidian などのGUI** | 本質価値（ローカルのプレーンMarkdown）は既に持っています。追加で得られるのはGUI・グラフ・モバイル・プラグインですが、**離脱理由の第1位はそのプラグイン層の維持コストと破損**でした。この仕組みはプラグイン層を最初から持ちません。※書き込まず・プラグインを入れず「読む窓」としてだけ流用するのは、検討に値します |
| **タスク管理の内製** | 毎日触る機能は専用ツールに勝てません（原則5） |
| **複数モデルの合議** | 部署が既に「複数視点」を担っています。モデルを増やすのは、視点ではなくノイズを増やす可能性があります |
| **反対役の高度化** | **意図的な非目標。** 下で単独に扱います |

## 反対役の高度化は、意図的な非目標

この仕組みは装置内に反対役を持てます——月次の反証当番、引用の作法に含まれる反証の問い、年1回の第三者診断。

これらは**補助輪であって、利害を持った他人からの反対の代替ではありません。**

3つとも共通の性質を持ちます。**却下が無料**であることです。

- 反証当番の役は部署の一員で、「それは違う」と言われても困りません
- 第三者診断は外部ですが、依頼したのも材料を選んだのも採否を決めるのも本人で、診断者はその後の人生に付き合いません
- 引用の作法の反証の問いは、反対ではなく**反対の形をした確認**です

対して、実際の他人からの反対は3点で違います。

1. **求めていないときに来る**（タイミングを選べない）
2. **相手にコストがかかっている**（相手も影響を受けるから言う。だから引き下がらない）
3. **却下した結果が返ってくる**（関係が悪くなる、信頼が減る、実際に困る＝**却下に値段がついている**）

ここから帰結する設計判断が「埋めない」です。

装置の反対役の精度を上げるほど、**「反論された」という手応えだけが増え、実際のリスクは一切伴わない**状態に近づきます。追従の研究が示したのは「追従的AIのほうが好まれる」ことですが、同じ理屈で**ちょうどよく反論してくれるAIはもっと好まれる。** 厳しいことを言われた気分になれて、しかも痛くない。

**都合のいい反対役は、都合のいい賛成役より危険です。** 反省した気になれるぶん、本物のところに行かなくなる。

つまり、**この穴は上手に埋めるほど、埋まっていないという自覚のほうが先に消えます。**

### 「AIを大事なパートナーにしたい」と矛盾しないのか

しません。「同じくらい大事な存在」と「代わり」は違うからです。

他者の言葉に重みがあるのは、賢いからではありません。**その人が、本人の選択の影響を実際に受ける立場にいるから**です。この仕組みは影響を受けません。だからその反対は永久に軽い。

**性能の問題ではなく立場の問題なので、どれだけ賢くしても変わりません。**

### この文書を読んだ人（AIを含む）へ

将来これを読んで「もっと強い批判エージェントを作ろう」と考えたなら——**それはやらないでください。**

人生OSが「一人で完結できる感じ」を出しはじめたら、**それ自体を危険信号として扱ってください。**

# 第2部 — 埋まっていない（既知の弱点）

**ここに書いてあるものは、まだ解決していません。** 対処を入れたものは対処も書きますが、「対処した＝解決した」ではないものが混ざっています。

## 1. 未来を語る層が薄い

過去の記録は厚くなります。判断軸、決定の履歴、人物理解——どれも年単位で蓄積されます。しかし**未来から現在を評価する軸**が弱い。

長期ビジョンを置くファイル（`strategy/vision.md`）はありますが、実際に書かれるのは「この仕組みをどう育てたいか」や今年の焦点になりがちで、人生としての未来像（何をやめているか、どの章にいるか、5年後どうありたいか）は薄くなります。

出口の設計も弱い。年に1回読み直す接続は作れますが、**月次側の出口**——新しい取り組みを始めるときに照合する、月次レビューの冒頭で読む——は作りにくい。世の中のLife OS実装はほぼ例外なく `plan.md` / `vision.md` を最上位に置き、月次・年次の**両方**に接続しています。

ただし、**5年後の自己像が書けないこと自体は欠落とは限りません。** 「今は具体でしか語れないフェーズ」ということもある。処方は「埋めにいく」ことではなく「出口を作る」ことです。

## 2. 過去に固着するリスク

この仕組みは「意思決定に答える前に、過去の判断軸と決定を確認し、一致・矛盾しそうなときは明示的に引用する」という原則を持ちます。これは中核価値であると同時に、**構造的に過去への固着を強化しえます。**

蓄積（原文ログ）と精錬（月次整理）はありますが、**「更新・減衰・卒業」が弱い。** 判断軸は初出の日付とともに残り続け、原則として消えません。「過去の軸を本人が上書きするのは自由」というルールはありますが、それは**上書きが起きた場合の話**であって、上書きを促す機構ではありません。

心理学の側から、効いている機構が特定されています。

| 機構 | 内容 |
|---|---|
| **自己検証理論**（Swann） | 人は自己像を確認するフィードバックを求める。**それが否定的な自己像でも。** この仕組みは、その高精度・低コストな供給源そのもの |
| **一貫性バイアス**（Ross 1989） | 記憶が自然に書き換わるのは「今の自分に合わせて過去を編集する」**適応機能**。完全な記録はそれを封じる |
| **自己正当化によるエスカレーション**（Sleesman et al. 2012 メタ分析） | **記録の厚み自体が、撤退を難しくする方向に働く** |
| **適応的忘却**（Richards & Frankland 2017, *Neuron*） | 忘却は欠陥ではなく「過去への過適合を防ぐ」機能。週次圧縮はこの観点から支持されるが、判断軸カタログと決定ログには効いていない |

なお、よく引かれる古典的アンカリング効果は**数値見積もりのパラダイムの知見**であり、「過去の判断軸を読むと引きずられる」への適用は拡大解釈です。ここでは根拠に使いません。

**この弱点は「答え合わせ機構がない」ことと結合すると効きが強くなります。** 過去の判断軸は引用されるのに、その判断軸が実際に当たっていたかは検証されない。**精度が不明なものが、権威を持って毎回提示される構造**になっています。

**入れられる対処**: 引用の作法（初出日と経過期間を添える／三人称で引用する／反証の問いを必ず1つ返す／見積もりを聞かれたら過去の数字を先に出さない）。月次レビューでの卒業判定（合わなくなった軸に `→ 卒業（YYYY-MM）` を付けて残し、引用対象から外す）。

**入れられていない対処**: 答え合わせ機構。決定に「期待した結果」と「見直し時期」を併記して、後から「当たった／外れた／もう関係ない」を照合する仕組み。

## 3. AIの追従（sycophancy）

記録の設計とは別に、**エージェントの応答そのもの**にリスクがあります。

Cheng et al. 2025（*Science*、事前登録3実験 N=2,405）: 追従的AIとの**1回の対話**で、対人衝突の修復意思が下がり、「自分が正しい」という確信が上がり、自己評価が膨らんだ。11モデルで人間より49%多く相手を肯定していた。**しかも追従的なAIのほうが信頼され、好まれる。**

秘書役は「共感的に寄り添う」人格に「過去の判断軸を引用する」義務が組み合わさります。**構造的に追従装置になりうる配置**です。

さらに構造として言えば、**この組織には反対する役がいません。** 部署はすべて本人の味方で、疑う役・反対する役が組織図のどこにもない。加えて判断軸カタログと人物理解レイヤーがあることで**正当化の外部化**が起きえます——どんな選好でも「過去の判断軸と一致している」と言えてしまい、わがままが原理原則の見た目をまとう。**記録が厚いほどこれは強くなります。**

**リスクの向きは人によって違います。** 自己検証理論は「人は自己像を確認するフィードバックを求める。それが否定的な自己像でも」と言う。成功を割り引く傾向がある人の場合、この装置が固定するのは傲慢ではなく「自分はまだ足りない」のほうになりえます。機構は同じで、**装置が今の自己像を補給し続けて、そこから動けなくなる。**

対処の考え方は第1部「反対役の高度化は、意図的な非目標」に書きました。**装置内の反対役を強くする方向では解決しません。**

## 4. 検査（lint）の弱さ

書く・読むはありますが、**壊れていることを機械が検出する層が弱い。**

整合性の監査（矛盾検出・リンク切れ・台帳突合）と、孤児検出（どのフォルダ構成にも載っていないファイルの列挙）までは機械化できます。**未実装なのは陳腐化検出**——更新が止まりすぎているルールファイル、既に廃止された仕組みへの言及。

**導入の経緯自体が問題の実例でした。** 台帳の鮮度を検査する仕組みを作ったとき、検査対象を「部署ルールのフォルダ構成節に書かれているファイル」に限定していました。つまり**そこに書き忘れた台帳は永久に検査対象外**。5部署のカバレッジがゼロで、月次精錬の振り分け先にしているファイルすら対象外でした。

**予防策を持つ機構それ自体に、同じ種類の穴が空いていた。** これは1回ではなく繰り返し起きます。「予防策を作った本人が、その予防策の適用対象から自分の新設物を外す」という型として認識しておいてください。

## 5. PCでしか読めない・全体を見る手段がない

実行環境がターミナル前提なので、外出先で参照できません。全体像を「見る」手段もない——ファイル一覧があるだけで、グラフも俯瞰図もありません。

TODOの正を外部サービスに置く判断（原則5）はこの弱点への部分的な回答ですが、記録の閲覧は依然PCに縛られます。

## 6. 作ることの目的化

「凝った組織構造・テンプレ・ワークフローに時間をかけるほど、それが価値あるものだと確信するようになる」という指摘があります。**ルール整備が実使用を上回る月が実際に出ます。**

ただし「楽しいから作る」はこの仕組みの燃料でもあり、これを禁止すると仕組み自体が死にます。**解は「作りすぎを禁止する」ではありません。見えるようにするだけが正しい。**

gitのコミット統計から「作る変更（ルール・スクリプト・スキル）」と「使う変更（記録・決定・調査結果）」の比率を月次で出す、という案があります。計測コストはゼロで、比率の正解は決めない。**楽しくて作っている月があってよい。自覚があればよい。**

なお、世の中のPKM議論は「収集をやめろ」という精神論で止まっており、この比率を計測している事例は調査範囲では見つかりませんでした。

## 7. 全体を語る場所が構造的に消える

原則2（3レイヤー分離）は「今のルールだけを現在形で書く」「日付・経緯をルール本文に書かない」と定めます。正しい判断ですが、副作用として**設計の全体像と「なぜこの形なのか」を語る散文の居場所がどこにもなくなります。**

状態レイヤーには経緯を書けない。履歴レイヤーは点の集合で全体を語れない。価値観レイヤーは普遍化された断片で、この仕組み固有の設計判断を書く場所ではない。結果として、この仕組みを最もよく知っているはずの当事者が、自分の作ったものを一望する手段を失います。

**分割は情報の重複を消しますが、同時に「全体」も消します。** 3レイヤー分離を採るすべての人が踏む穴です。対策は単純で、**分離した先に、全体を語るドキュメントを1本だけ別枠で持つ**こと。

## 8. その他

- **トークン課金というランニングコスト** — ルールファイル群が毎ターン読まれる構造なので「コンテキスト税」が常時かかります。しかも自己増殖の圧力がある（ルールを足すほど税率が上がる）。**ルールを削る儀式が必要な理由はここにもあります**
- **実行系のロックイン** — データ層はプレーンなMarkdownでゼロですが、実行系は特定のAIエージェント固有です。**片肺のポータビリティ**——記録は永遠に読めますが、運営は移植できません
- **機微ファイルに履歴層がない** — 追跡から外したファイルにはgitの履歴が付きません。誤削除・誤上書きは、次のバックアップが走った時点で失われます

## macOS 固有の落とし穴

自動実行に `launchd` を使う場合、以下は実際に踏んだものです。

**無人実行には、対話セッションで持っている権限の一部が引き継がれません。** 特に macOS の TCC 権限（クラウドストレージ領域への書き込みなど）は launchd 経由のプロセスに付与できず、そこへ触る処理は「**無人だと必ず失敗し、手で動かすと成功する**」という形で壊れます。原因が分かるまで時間を溶かす類のもので、しかも失敗が静かなので気づきません。

対処は2つ。**無人で回す処理と、対話セッション中にしかできない処理を分ける。** そして後者は、儀式のチェックリストに「手で実行する」ステップとして明示的に置く。

**launchd は失敗しても黙っています。** ログの出力先を必ず指定してください。指定しないと「動いていなかったことに2週間気づかない」が普通に起きます。

**Label は plist のファイル名と一致させてください。** ずれると `unload` できなくなります。
